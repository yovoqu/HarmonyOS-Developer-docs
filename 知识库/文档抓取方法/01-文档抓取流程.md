# 文档抓取流程

合并自：[[文档抓取方法论]]、[[华为开发者文档抓取实战规范]]、[[华为开发者文档拉取经验总结]]

---

## Phase 0: 范围确认

开始前确认 4 件事：

1. **抓什么范围** — 哪些 catalog、哪些模块
2. **怎么分类** — 本地目录映射关系
3. **最终目录长什么样** — 先建目录，再抓内容
4. **landing page 要不要** — HTML 归档保留，Markdown 产出不保留

如果跳过这一步，最常见的问题是：抓多了、抓偏了、分类不一致、产物需要返工。

## Phase 1: 获取导航目录

### 1.1 优先使用 getCatalogTree API

```python
resp = session.post(
    "https://svc-drcn.developer.huawei.com/community/servlet/consumer/cn/documentPortal/getCatalogTree",
    json={"language":"cn","catalogName":"harmonyos-guides"}
)
tree = resp.json()["value"]["catalogTreeList"]
```

### 1.2 提取叶子节点

递归遍历 `catalogTreeList` → `children`，收集所有 `isLeaf: true` 且含 `relateDocument` 的节点。`relateDocument` 即为文档 slug。

### 1.3 目录树清洗

官网导航树中可能插入冗余中间层级（如"开发"、"指南"）。构建本地路径时需过滤无意义的中间节点名。

### 1.4 用户分类与官网分类的映射

官网一级节点不一定对应用户期望的分类目录。抓取前先输出完整节点列表，让用户确认映射关系。

## Phase 2: 差异对比

### 2.1 批量获取官方更新时间

```python
def fetch_doc(catalog, slug):
    resp = session.post(API_URL, json={
        "objectId": slug, "version": "",
        "catalogName": catalog, "language": "cn"
    })
    val = resp.json()["value"]
    return val["title"], val["displayUpdateTime"], val["content"]["content"]
```

对所有已收录文档的 slug 调用此 API，获取 `displayUpdateTime`，与本地 Markdown 中的 `更新时间` 对比。不一致则标记为需更新。

### 2.2 新增文档检测

将 Phase 1 获取的全量叶子节点 slug 与本地 manifest 条目做差集：
- `official_slugs - local_slugs` = 新增文档（需拉取）
- `local_slugs - official_slugs` = 已下线文档（需标记）

## Phase 3: 拉取正文

### 3.1 单文档拉取

直接使用 `getDocumentById` API（不需要 Playwright）。返回的 `content.content` 即为完整 HTML 正文。

### 3.2 图片处理

见 [[03-图片资源规范]]。核心原则：
- 优先复用本地已有 assets（图片内容极少随文档更新而改变）
- 新图片按 `file-{timestamp}-{hash}.{ext}` 命名存入 `assets/{docName}/`

### 3.3 断点续传

千级以上文档必须设计检查点：
- 每批次完成后即时写入 manifest
- 重跑时读取已有 manifest 跳过已完成项

## Phase 4: HTML → Markdown

详见 [[02-HTML转Markdown规范]]。

## Phase 5: 后处理

转换完成后必须对全量 Markdown 执行自动化后处理：

1. **清除 `[h2]/[h3]/[h4]` 标记** — API 返回的标题文本含这些前缀
2. **图片引用独立成行** — 与正文文本拆分
3. **行首空格清除** — 段落前导 2+ 空格去除（保护代码块、列表、表格、引用）
4. **段落内连续空格压缩** — 4+ 空格压缩为单空格
5. **API 元数据间距** — references 文档的 `**xxx：**` 行之间插入空行

## Phase 6: 质量检查

### 检查清单

- [ ] 各目录文件数是否合理
- [ ] manifest 条目数与文件数是否对应
- [ ] 是否存在 404 页面混入
- [ ] 更新时间是否更新
- [ ] 表格是否有分隔线（`|---|---|`）
- [ ] 代码块是否有缩进
- [ ] 是否残留 `[h2]/[h3]/[h4]` 标记
- [ ] 图片引用是否独立成行
- [ ] API 文档是否有 `支持设备：` 元数据
- [ ] **子标题（h2/h3/h4）的设备类型是否保留** — 官网 HTML 中各级标题均可带有 `device-type` 属性，转换时每级标题都需单独输出 `**支持设备：**` 行
- [ ] **是否使用了完整版 `html_to_markdown()`** — 任何简化版转换器都会丢失数据，严禁用于正式拉取

### 已验证的常见陷阱（2026-07-01）

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用简化版 HTML→MD 转换器拉新文档 | 子标题 device-type 全部丢失 | 始终使用 `fetch_docs.py` 中的完整 `html_to_markdown()` |
| 修复问题时只处理新增文件（`--diff-filter=A`） | 被误修改的存量文件未修复 | 必须包含 `--diff-filter=AM`（新增 + 修改） |
| FAQ 目录的 manifest 更新到根目录 | 条目未写入任何 manifest | FAQ 使用子目录级 manifest，需按树路径定位 |
| **manifest file 字段路径基准错误**（写成相对仓库根） | check_updates 再拼一次 manifest 目录 → 双重前缀路径 → fetch_docs 在错误位置创建文件 | `file` 必须相对 manifest 所在目录；写入后用 `(manifest_dir / file).exists()` 校验 |
| **拉取新文档后未同步更新 manifest** | 已存在的文件不在 manifest 里 → 每次检测都误报"新增" → 重复拉取 | 拉取与 manifest 更新必须原子完成 |
| **manifest 重复条目（同 slug 两次）** | 文件路径冲突、去重困难 | 写入前先查 slug 是否已存在；定期全量去重 |
| **catalog 判断顺序错误** | `设计指南` 在 `指南`/`最佳实践` 之后 → 设计指南 manifest 被当作 guides/best-practices 查询 API → 文档被跳过或拉错 | catalog 判断必须**最长匹配优先**：`设计指南` 先于 `指南` 和 `最佳实践`；`设计/设计指南` 先于 `开发/最佳实践` |

### Catalog 判断顺序（必须最长匹配优先）

`catalog_for_manifest()` 中 `设计/设计指南` 同时包含"设计指南"、"指南"、"最佳实践"（应用设计最佳实践）子串，判断顺序错误会导致：
- 设计指南 manifest → 被当成 `harmonyos-guides`（错误 catalog 查询 API）
- 应用设计最佳实践 manifest → 被当成 `best-practices`

正确顺序（2026-08-11 修正）：

```python
def catalog_for_manifest(manifest_path):
    rel = str(manifest_path.relative_to(BASE))
    if "设计指南" in rel:
        return "design-guides"      # ← 必须先判断（最长匹配）
    if "指南" in rel:
        return "harmonyos-guides"
    if "API参考" in rel:
        return "harmonyos-references"
    if "FAQ" in rel:
        return "harmonyos-faqs"
    if "最佳实践" in rel:
        return "best-practices"     # ← 在 设计指南 之后
    if "版本说明" in rel:
        return "harmonyos-releases"
    return "unknown"
```

**教训**：路径分类判断必须按"最长匹配优先"排序，否则含子串的目录会被错误分类，且错误是静默的（文档被跳过、用错 catalog 查询），需要全量复查才能发现。

### Manifest 维护铁律（2026-08-11 教训）

1. **`file` 字段 = 相对 manifest 所在目录的路径**。写错基准会引发连锁故障：`check_updates` 拼接出 `开发/FAQ/{sub}/开发/FAQ/{sub}/...` 双重前缀路径，`fetch_docs` 按此在磁盘创建错误目录树（实测 2,836 个错误文件）。
2. **文件拉取与 manifest 更新必须同时完成**。FAQ 曾因只拉文件没写 manifest，导致 2,895 篇已存在文档每次全量检测都被误判为"新增"。
3. **写入前检查 slug 去重**（同 manifest 内），避免重复条目。
4. **每次操作后用完整性校验兜底**：遍历所有 manifest，`(manifest_dir / file).exists()` 必须全真；`file` 字段不得包含 `开发/FAQ/` 等仓库根前缀；文件路径不得出现重复段（如 `NDK开发/NDK开发`）。

## Phase 7: 新增文档拉取（独立流程）

当检测到官网有新文档（`official_slugs - local_slugs`）时，拉取流程：

1. 调用 `getCatalogTree` 获取完整目录树 + 所有叶子节点 slug
2. 对比本地 manifest slugs，找出新增项
3. **关键**：使用 `fetch_docs.py` 中的完整 `html_to_markdown()` 函数进行转换，**严禁**编写简化版转换器 —— 简化版必然会遗漏 device-type、note callout、rowspan 等细节
4. 按目录树路径确定本地文件路径（见 [[05-目录划分与文件存放规则]]）
5. 更新对应目录层级的 manifest.json（FAQ 需注意子目录级 manifest）
6. 拉取完成后运行 Phase 6 质量检查

## manifest 规范

```json
{
  "group": "分类路径",
  "slug": "文档slug",
  "name": "文档标题",
  "file": "相对路径/文件名.md",
  "url": "https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/slug",
  "title": "文档标题"
}
```

字段说明：
- `group`：目录分组路径
- `slug`：官网 URL 尾部标识
- `file`：本地文件**相对 manifest 所在目录**的路径（⚠️ 不是相对仓库根）
- `url`：官网来源完整 URL

示例（manifest 位于 `开发/FAQ/应用框架开发/manifest.json`）：
```json
{ "slug": "faqs-arkui-1", "file": "UI框架/组件使用/xxx.md", "url": "..." }
```
`file` 解析基准 = manifest 所在目录，即 `开发/FAQ/应用框架开发/UI框架/组件使用/xxx.md`。

## 异常处理

### 异常 slug
URL 命名不符合规律但页面有效 → 按同组规则修正本地文件名，manifest 中同步更新。

### 404 页面
标题为 `404` 或正文非目标内容 → 不保留，从 manifest 剔除。

### API 返回 document not found (code: 92531031)
说明 catalogName 不正确或文档已下线 → 检查 catalog 映射表。

## 清理原则

任务完成后保留：
- 最终 Markdown 文件
- `manifest.json`
- assets 目录

任务完成后删除：
- 临时脚本
- 调试输出
- 中间 HTML 文件
- 缺失 URL 列表
